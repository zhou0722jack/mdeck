# App 入口 JIT 与 A/B/C 内存池

本次修改把 JIT 请求放在 `MadeiraApp.init` 的起点，与 App 初始化和启动动画并行。
不等待根视图、启动动画结束、组件下载或点击启动 Steam。首次选择另一种 JIT 方式时，
仍走统一协调器取消旧的等待并加入新请求，不同时启动两个调试器。

## 生命周期

1. App 映像加载时，原生构造函数先保留 EXE 窗口和原有 A 区占位。
   随后在主线程栈上方寻找 B 区，在 EXE 窗口下方寻找 C 区，用固定地址、禁止覆盖的
   `PROT_NONE` 映射保护实际空闲空间。不移动栈或系统映射，不把占位当作可执行内存。
2. C 的早期占位按全局 `pool-low-margin` 计算，默认 128 MB；最低 64 MB。
   下方另一段足够大的空闲区可以承担保留量。占位本身不触碰对应页面。
   此时尚不知道下一次启动哪个游戏，实际分配时会重新检查 Steam 配置、保留量和剩余空间。
3. App 初始化立即请求已保存的 JIT 方式；第一次打开使用默认的脚本方式。
   外部脚本模式仍需用户在 StikDebug 中运行绑定本 App 的脚本，App 不会自行绕过调试器附加。
4. 协调器确认调试器就绪后立即建立 A/B/C 可执行池。配置快照在 App 初始化返回后的
   下一次主队列调度取得，确保读取已安装的全局默认值和 Steam 运行配置；不修改活动游戏环境变量。
   Steam 运行配置覆盖全局同名键，`pool` 仍限制为 256～1152 MB。
5. 在 A/B 分配开始时释放早期 B 占位；C 占位继续保留到申请 C 时。
   C 关闭、没有合适的主池布局、转换失败或准备提前结束时，只释放仍属于自己的占位。
   释放成功后清除所有权；后续重复调用不会把调试器或运行时在相同地址建立的映射释放掉。
   释放失败保留所有权并记录错误，不将该地址当作可用 C。
6. 入口分配与快速点击启动共享一把锁和同一组缓存映射。入口探测在池准备完成后开始，
   每 5 秒直接借用现有 A/B/C 区各 8 字节，写入 `mov x0,#42; ret`，执行后恢复原始字节。
   不再创建独立探测缓冲区，也不在正式池中永久保留探测页；描述符只是现有映射的范围。
   A 避开既有首个 trampoline 页，B 从实际成功分配的 B 区取地址，C 使用已验证的低地址别名。
   三区各自记录执行结果；没有 B/C 时显示未分配，只有三区均分配并返回 42 才显示绿色。
   启动 Steam 前等待正在执行的一轮恢复完成，随后原生探测器单向封闭，不再允许执行。
   生产 A/B/C 不释放；Wine 启动读取同一组池、空洞与 C 元数据，不再次发起分配。
7. 大池分配失败会结束本次入口准备并拒绝已排队的 Steam 启动；不会自动重复消耗映射。
   在调试器尚未附加时不会发起未被处理的池分配 BRK。
   若调试器已在主界面等待期间离开，启动时直接复用池并跳过 detach BRK。
   探测直接执行现有可执行映射，不再依赖调试器持续附加，也没有每轮 BRK。
   任一已分配区探测失败会停止后续探测；发生在排队启动期间同样拒绝启动 Wine。
   原始内容恢复失败必须重开 App，不能交给 Wine/FEX 继续使用。

## 容量和设置生效时机

A/B 的现有范围仍受 `0x180000000` 上界、EXE 窗口和已存在的线程栈限制。
在主池从 `0x148000000` 开始的布局中，地址跨度上限仍是 896 MB，实际可用量要扣除空洞。
C 独立计算；早期预留不能保证 A+B 达到 1152 MB，也不能保证一定有满足 64 MB 下限的 C 区。

池在 App 入口建立后，池大小、拆分、C 保留量和别名布局的修改需要彻底关闭并重新打开 App。
同一进程内优先复用已有池，不在活动池上调整地址。若后续程序要求比入口池更大的 EXE 加载窗口，
会拒绝启动并提示先在 Steam 运行配置中设置 `exe-window-mb` 后重开 App。
其他运行时设置继续通过原有启动流程应用。

## 诊断记录与验证边界

- `[jit-entry] requesting selected JIT method immediately at app entry`：初始化处发起请求。
- `[jit-entry-hold] B/C protected at image load`：进入 Swift 分配时记录原生早期占位快照。
- `[jit-entry-pool] allocating A/B/C immediately after attachment`：附加后开始分配。
- `[jit-entry-pool] ready`：记录申请目标、主池跨度、扣除空洞后的主池可用量、C 与合计可用量。
- `[jit-entry-pool] reusing A/B/C prepared at app entry`：后续启动复用，没有再次分配。
- `[jit-entry-probe] A/B/C`：现有区内实际借用的地址及各区返回值，未分配区明确标记。

`check-entry-jit-pool.py` 编译生产预留、释放和缓存代码，以注入的 VM/调试器适配器检查边界、
加载余量、失败清理、并发一次分配和一次移交；同时对完整原生分配器与 Swift 分配器做 iOS SDK 检查。
`check-app-entry-jit.py` 检查无视图时立即请求、延迟附加/池准备、快速启动等待、失败拒绝及三区借用和交接生命周期。
`check-abc-jit-probe.py` 对生产 C 探测器进行 iOS SDK 检查，以及本机 ARM64 真实小代码执行、
ASan/UBSan 下的 1000 轮三区执行与原文恢复；覆盖缺区、假别名、部分写入/执行异常、恢复失败、
宿主信号转发和一次交接。探测器不调用分配、释放、重映射、改保护或调试器接口。
这些结果属于本机组件和类型检查；iPad 上实际可用地址、真实 BRK 交接、三区执行权限、主界面驻留内存与 Steam 运行仍需真机验证。
本次不构建 IPA。
