# 首次启动与组件准备

当前分支：`codex/droiddeck-ui`。实现位于 `app/Madeira/DeckStartup.swift`。

首次打开的顺序：

1. 在一个页面中选择 **脚本 JIT** 或 **内置 JIT**。
2. 点击“继续”，即按所选方式请求/等待 JIT，同时播放 DroidDeck 启动动画，然后进入 Steam 首页；此时不下载运行组件。
3. 点击“启动 Steam”，检查四项组件，缺失项同时开始下载，全部就绪后自动进入原有 JIT 和 Steam 启动流程。

脚本方式可以直接导出 `madeira-jit.js`，由 StikDebug 执行；内置方式可以打开
现有的配对、导入配对文件和 LocalDevVPN 设置。LiveContainer 环境保留脚本方式，
内置选项会显示不可用原因。选择只保存一次，以后在“设置 → JIT”中更改。
已有选择时，每次新进程进入 App 即请求/等待 JIT，仍使用现有附加后端，没有修改 JIT 脚本。
就绪且有调试器附加时，先执行一次独立 16 KiB 探测，之后前台每五秒执行并回收；后台暂停，不重叠执行。
启动 Wine/Steam 前停止循环并等待当前轮清理，随后才申请原来的主 JIT 池。探测失败停止重复执行，释放失败要求重开 App。
该探测生成一段返回 42 的 ARM64 小代码，不预先启动 FEX，也不清空或替代 Steam 的主池。

原来的欢迎、安装 VPN、Steam 登录、快捷指令、逐项运行库介绍及完成页已删除，
“重新运行引导”按钮已移除。Steam 登录、配对、各运行库和图形/显示设置仍在原有分类。

## 启动动画

使用 DroidDeck 0.6.9 默认的原始 `droiddeck-startup.webm`，保留原画面和音效，
转换为 iOS 原生 AVPlayer 使用的 H.264/AAC MP4。画面为 1280×720、30 帧，
共 190 帧，时长约 6.35 秒。来源提交、转码参数和哈希记录于
`droiddeck-startup-asset.json`；许可证和来源声明随动画一起打包。

后续每次冷启动播放一次；从后台返回不重播。进入后台暂停，返回后继续。
启动页不显示跳过按钮；双击视频区域跳过动画。组件准备在点击“启动 Steam”时单独显示，
跳过启动动画不会标记组件已就绪。VoiceOver 另提供“跳过动画”辅助操作。
播放失败或卡住时可继续进入界面，播放器退出时释放。系统开启“减少动态效果”时跳过。
“设置 → 启动器”提供播放开关、音效开关和预览。

## 自动准备的四项组件

| 组件 | 实际动作 |
| --- | --- |
| Wine Mono | 从 WineHQ 下载固定版本，校验 SHA-256、解压并安装；已有可用版本时跳过 |
| Microsoft Visual C++ | 使用现有固定版本安装器下载、校验和 DLL 提取流程，检查已安装版本 |
| Wine Gecko | 从 WineHQ 下载并校验两个已有架构的 MSI，供 Wine 使用 |
| Madeira Dock | 检查包内 Dock 宿主，使用原有安装服务下载并校验 Valve 客户端组件 |

界面显示每项真实的下载、解压或验证状态。Dock 下载器只提供阶段文本时显示不定进度，
不生成虚构百分比。组件准备本身不启动 Wine，也不申请主 JIT 池；进入 App 的独立小缓冲探测可以同时进行。

点击“启动 Steam”时按实际文件检查四项组件，不依赖旧的完成标记。四项缺失组件并行准备，
每项内部继续使用原来的下载、校验和安装顺序。下载过程中保留每项状态，全部就绪后，
同一个加载层切换到启动阶段，只继续一次原有启动流程。已就绪的直接跳过；设置中已有下载任务时等待该任务，不重复下载。

网络或空间不足等失败会保留原因，点击“重试下载”仅补齐缺失项。全部下载任务结束后，
失败页面可选择“返回主界面”，取消这次自动启动；下次点击“启动 Steam”时再检查并补齐，
不会重新询问 JIT 方式。原有“组件”与诊断页面的手动准备入口继续保留。

## Steam 首页

首页只显示一个“启动 Steam”操作。四项组件准备完成后，尚未安装交互式 Steam 客户端时，此按钮启动
原有内置 Steam 安装程序，下方说明首次安装行为；安装后启动客户端。
安装器直接作为初始程序运行，不先创建 explorer 桌面或服务脚本；旧的安装器条目
在推荐配置处理前后都会规范化启动路径。安装器进程错误由现有初始进程退出监测报告。
JIT 附加仍由原有启动检查按所选方式执行。首页不再放置独立的安装器、JIT 或 Dock 设置按钮。
侧栏和其他页面保留，以继续访问图形、显示、手柄、运行库和诊断。

## 当前验证边界

### 点击 Steam 后的三阶段动画

`DeckSteamLoading.swift` 将 DroidDeck 的 `LogoThrobber`、`LoadingOverlay` 和 `TiltedWall`
移植为 SwiftUI Canvas：1.9 秒标志变形/旋转及色球缩放、65 秒倾斜封面墙漂移、暗色遮罩和三段进度。
来源和固定提交哈希见 `droiddeck-steam-loading.json`；只读取已有本地封面，不额外下载封面抢占组件带宽。

1. 下载/验证组件：显示真实组件状态，全部就绪后保持加载层，进入下一阶段。
2. 启动 Steam：继续使用原有 JIT 和执行链。配对界面需要操作时暂时让出，返回继续同一启动状态。
3. 等待目标窗口首帧：使用窗口进程路径及实际可见图层内容，拒绝桌面、控制台、Dock 的另一份 Steam、
   隐藏窗口、空图层和仅创建的交换链。Steam 主程序或同一客户端目录下 CEF 帮助进程的有效画面才结束加载。

安装器尚需交互时，单独等待安装器自身的可见画面并标注“Steam 安装程序”，不会称为 Steam 已启动。
等待超过两分钟只显示较慢提示并继续监听，不靠倒计时关闭。组件/JIT/进程错误显示日志与恢复操作；
取消或重试会更换请求标识，旧 JIT 回调不能再启动程序。用户请求关闭会话时沿用原有退出机制。

窗口图像必须已交给可见的 GDI/CEF 图层；当前交互式 Steam 的启动参数继续禁用 CEF GPU。
本次没有更换 Steam 客户端、JIT 脚本或图形后端。

已运行实际启动模型和 Steam 启动入口的异步行为测试，下载服务以测试替身提供；覆盖首次/再次打开不下载、
四项并发、缓存跳过、失败重试、失败后返回、重复请求、等待已有准备任务、移除组件后的重新检查、
运行中会话及缺失 Dock 的拒绝，以及三阶段持续覆盖、首帧归属、慢启动、退出和旧请求回调失效。
新启动视图与 AVPlayer 桥接已在 iOS SDK 下配合依赖替身通过类型检查。
已检查动画媒体、190 帧完整性和转码画面对比，整体 SSIM 为 0.995711。

完整 IPA 通过 GitHub Actions 的 `Build IPA` 工作流生成。最近打包版本为 Build 12，
Build 13 的源码包含“点击 Steam 时并行准备组件”、连续加载层和进入 App 的独立 JIT 探测；
云端构建和包内容核验之外，实际联网下载和探测执行仍需 iPad 验证。
源码测试和打包检查均不能替代 iPad 上的动画声音、实际网络下载及 Steam 启动验证。
此前的 Build 8 IPA 不包含本轮更改。

## Build 9 安装器反馈后的源码调整

2026-11-07 的 `SteamSetup.exe-2026-11-07_06-10-38.txt` 显示 JIT 成功准备并解除附加，
explorer 创建了 SteamSetup 子进程；该子进程加载 `xtajit.dll` 的 native WoW64 依赖时
在 kernelbase 字符转换代码中触发访问异常，随后 CPU 后端加载失败，退出 `0xc0000135`。
这解释了桌面仍在而安装器窗口未出现；不能把它归因于没有发出启动命令。

本次改为安装器初始进程启动，以避开此处 explorer 子进程加载路径，并让原有退出
监测能报告安装器的错误。该路径已通过生产 `LibraryEntry.configureLaunch()` 的宿主测试，
但不代表 WoW64 后端已经修复或 Steam 已在 iPad 上运行成功。
双击跳过和这次安装器路径调整从 Build 10 开始打包；已有 Build 9 包仍采用旧路径。
本轮本机交互测试已由用户取消；不把模拟器测试程序的编译视为 Steam 或双击手势实测通过。

## Build 11 的跟踪与异常诊断修正

`06-58-22` 日志确认配置中已启用 `env.MADEIRA_DEBUG_VERBOSE=1`，但原来的日志级别
选择发生在配置环境变量导出之前。新的 `build/madeira_debug.h` 直接读取全局和游戏配置，
在 wineserver 启动前及 guest 启动前选择日志通道。开启“扩展日志”时额外加入
`trace+msvcrt` 和 `trace+nls`，并写出 `[wine-debug]` 行确认实际选择。
关闭扩展日志时不追加这两个通道，也不输出这条详细设置记录；用户手动配置的
Wine 追踪选项仍按自己的配置工作。
这避免“配置显示已开启，Wine 初始化却缓存了此前默认通道”的时序问题。

同一次运行先在 `kernelbase!wcstombs_codepage` 触发异常，退出后，系统线程在无 Wine TEB
时进入 `handle_syscall_fault`，再次访问空指针并产生重复异常。该处理函数现在先检查
TEB 和 syscall frame，无 Wine 状态时返回，不再把宿主线程当成 Wine syscall 处理。

宿主测试已执行实际日志选择函数和实际异常处理函数，覆盖全局/游戏/环境配置优先级、
缺少 TEB、缺少 frame、非 syscall，以及 Wine 的异常跳转与正常返回。
这两项修改改善日志生效与异常处理；字符转换表首个访问异常尚未修复，不能视为 Steam
安装成功。这些修改从 Build 11 开始打包，现有 Build 10 IPA 不包含。

新增 CRT 调用来源诊断保存在 Madeira 自己的
`build/windows-runtime/patches/0001-crt-invalid-parameter-callsite.patch`。
构建时应用于固定版本的 Wine，不更改子模块提交。失败检查会记录表达式、函数、
源码位置和调用地址，参数处理器收到的原始参数、errno、处理器优先级及致命异常均保留。
`madeira_crt` 专用通道实时读取“扩展日志”开关，不缓存开关值：关闭后停止新增详细输出，
原有错误行仍保留。开关关闭时不进行格式化或调用栈采集。

`tests/host/check-crt-callsite-diagnostics.py` 编译补丁后的实际检查宏与错误处理函数，
覆盖正常路径无输出、开关切换、errno 保留、参数单次求值、处理器参数与优先级、
致命异常及 noreturn 退出。它是宿主语义测试，不代表完整 Windows DLL 编译或 Steam 实测。
